1. EXECUTIVE SUMMARY
The AI-Powered Research Collaboration & Intelligent Team Formation Platform is a centralized digital ecosystem designed to solve the fragmented, inefficient, and unreliable process of finding research collaborators in academic environments.
Today, students and researchers rely on informal channels—WhatsApp groups, Telegram, LinkedIn, college notice boards, and personal networks—to find teammates for research projects, hackathons, final-year projects, and publications. These methods are slow, biased toward existing networks, and provide no reliable signal about a candidate’s actual skills, research interests, or experience.
This platform replaces that chaos with a structured, AI-assisted workflow:
Discover projects and researchers through intelligent search and recommendation.
Match using AI-estimated compatibility scores based on skills, research interests, evidence, and role fit.
Form teams using AI-recommended balanced team combinations.
Collaborate inside private project rooms with tasks, research notes, documents, discussions, and GitHub integration.
Track progress through activity logs, milestones, and analytics.
The platform is built on Supabase (Auth, PostgreSQL, Row Level Security, Storage, Edge Functions) with a React + TypeScript + Tailwind CSS frontend and a provider-agnostic AI layer (Gemini or OpenAI). It follows a strict principle: AI recommends, humans decide.
This PRD is the single source of truth for development. It is designed to be implementable in phases—starting with a hackathon-ready MVP and scaling toward a multi-institution academic collaboration platform.
2. PRODUCT VISION
To become the default digital environment for academic research collaboration, where any student, researcher, or faculty member can discover the right project, find the right collaborators, form a balanced team, and manage research and development—all in one secure, AI-assisted workspace.
Vision Statement: > “From scattered WhatsApp messages to structured, AI-assisted research collaboration.”
The platform bridges the gap between: - Discovery (finding projects/people) - Evaluation (assessing compatibility) - Formation (building balanced teams) - Execution (collaborating on research and code)
3. PROBLEM STATEMENT
Students and researchers struggle to find suitable teammates for research projects, academic projects, hackathons, publications, and technical innovation. Existing platforms are not designed for research-team formation.
This results in: - Wasted time searching through informal channels. - Unreliable skill verification. - Poor team composition (duplicate skills, missing roles). - Overwhelmed project owners reviewing many applicants manually. - Fragmented collaboration across multiple disconnected tools. - No centralized record of contributions, research notes, or project history.

5. PROPOSED SOLUTION
An AI-powered ecosystem combining:
Researcher Discovery + AI Matching + Team Formation + Project Rooms + GitHub Collaboration
Users can: - Create research-oriented profiles (student or faculty). - Publish or discover research projects. - Define required skills and roles. - Apply to join projects or invite collaborators. - Receive AI-generated compatibility analysis with explanations. - Receive AI-recommended balanced team combinations. - Connect GitHub for evidence-based skill analysis. - Collaborate inside private project rooms. - Track tasks, research notes, documents, and activity. - Maintain project history and contributions.

14.3 Progressive Onboarding (Post-Verification)
Step 1: Basic Profile (Required) - Profile photo (optional) - Institution, Department (pre-filled) - Academic year / Designation (pre-filled)
Step 2: Skills (Required — min 3) - Select from skill taxonomy - Set proficiency: Beginner / Intermediate / Advanced - Add custom skills
Step 3: Research Interests (Required — min 2) - Select from interest taxonomy - Add custom interests
Step 4: Experience (Optional) - Add past projects - Add internships - Add certifications
Step 5: External Profiles (Optional) - GitHub OAuth - LinkedIn URL - Portfolio URL
Step 6: Collaboration Preferences (Optional) - Preferred roles - Availability (hours/week) - Preferred team size
Users can skip optional steps and complete later. Dashboard shows profile completeness.
14.4 Institution Verification (MVP: Simple)
For MVP: - User selects institution from a pre-populated list (or types it). - No verification required initially. - Optional: email domain check (e.g., .edu, .ac.in) for “verified student” badge.
For Phase 2: - Institution admin accounts. - Domain-based auto-verification. - Manual verification for edge cases.

16. AI PROFILE ANALYSIS
16.1 Purpose
Provide evidence-based skill assessment without falsely claiming expertise.
16.2 Input Data
Self-declared skills
Project descriptions
GitHub repositories (if connected)
Publications
Certifications
Research interests
16.3 Processing
PROFILE DATA COLLECTION(Self-declared skills + Projects + GitHub + Publications)              |              vEVIDENCE AGGREGATIONFor each skill, find supporting evidence:  - Projects mentioning skill  - GitHub repos with language  - Publications with keywords  - Certifications              |              vAI ANALYSIS (Edge Function)Prompt: "Given this evidence, estimate skill confidence"Output: Structured JSON with confidence levels              |              vVALIDATION & STORAGE  - Validate JSON schema  - Store in ai_analyses table  - Display to user (private)
16.4 Output Format
{  "skill": "Python",  "confidence": "high",  "evidence": [    "5 related projects",    "Multiple Python repositories on GitHub",    "Relevant project descriptions"  ],  "self_declared_proficiency": "advanced",  "evidence_supported": true,  "note": "Evidence suggests strong practical experience. This is an AI estimate, not a certification."}
16.5 Important Constraints
AI must never claim objective expertise.
Use terms: “evidence-supported”, “AI-estimated”, “confidence level”.
User can always view and contest AI analysis.
AI analysis is private to the user by default.

Project owner can define custom roles. Each role has: - Name (e.g., “ML Engineer”) - Description (e.g., “Builds and trains ML models”) - Required skills (optional) - Number of openings (default: 1)
Default role templates (can be customized): - Project Lead - Researcher - Machine Learning Engineer - Data Scientist - Frontend Developer - Backend Developer - UI/UX Designer - Research Writer - Reviewer - Faculty/Mentor
19. PROJECT DISCOVERY
19.1 Discovery Page
The Explore Projects page provides a search bar, filters (Domain, Skills, Difficulty, Type, Sort), and a scrollable list of project cards. Each card shows the project title, domain, required skills, open roles, team fill ratio, difficulty, deadline countdown, and an AI-estimated match percentage, with “View Details” and “Apply” actions. A “Load More” control paginates additional results.
19.2 Ranking System
Project recommendations use a hybrid ranking:
Final Score = w1 x Skill Match            + w2 x Interest Match            + w3 x Role Match            + w4 x Experience Match            + w5 x Recency            + w6 x Availability
Where: - Skill Match: Deterministic overlap between user skills and project required skills (0-1). - Interest Match: Overlap between user research interests and project domain (0-1). - Role Match: Whether user’s preferred roles align with open roles (0-1). - Experience Match: User’s experience level vs. project difficulty (0-1). - Recency: Projects published recently rank higher (0-1). - Availability: User availability vs. project duration (0-1).
Weights are configurable and stored in a config table.
AI augmentation: For semantic search, embeddings are used to find projects matching natural language queries.

22.5 Scoring Framework
The overall score is a weighted combination of sub-scores:
compatibility_score = 0.35 x skill_match                    + 0.25 x interest_match                    + 0.20 x role_match                    + 0.20 x experience_match
Weights are configurable. The AI provides sub-scores based on evidence; the backend computes the final weighted score deterministically. This prevents the LLM from arbitrarily inventing a final score.

27. AI TEAM FORMATION
27.1 Purpose
Given a project and a pool of applicants, recommend a balanced team combination.
27.2 Input
Project required roles
Project required skills
Applicant pool (with compatibility scores)
Team size constraints
27.3 Algorithm
This is a constrained optimization problem, not a pure LLM task.
Step 1: Deterministic Pre-processing - Filter applicants by minimum compatibility threshold (e.g., > 60%) - Group applicants by role
Step 2: Optimization - Use a greedy or Hungarian algorithm to assign applicants to roles - Maximize: total skill coverage + role coverage - skill duplication - Constraint: each role filled by at most one applicant - Constraint: team size within min/max
Step 3: AI Post-processing (optional) - AI reviews the recommended team - AI provides qualitative assessment - AI suggests alternative combinations if needed
Step 4: Explainability - Show which roles are covered - Show skill coverage - Show any gaps - Show alternative candidates per role

{  "recommended_team": [    {      "role": "ML Engineer",      "candidate": {"user_id": "uuid", "name": "Rahul", "compatibility_score": 94}    },    {      "role": "Research Writer",      "candidate": {"user_id": "uuid", "name": "Priya", "compatibility_score": 89}    },    {      "role": "Backend Developer",      "candidate": {"user_id": "uuid", "name": "Arjun", "compatibility_score": 92}    },    {      "role": "Frontend Developer",      "candidate": {"user_id": "uuid", "name": "Karthik", "compatibility_score": 88}    },    {      "role": "Data Scientist",      "candidate": {"user_id": "uuid", "name": "Divya", "compatibility_score": 90}    }  ],  "team_skill_coverage": 95,  "role_coverage": 100,  "skill_duplication": "low",  "gaps": [],  "reason": "This team covers all required roles with strong skill alignment. users has a one-to-one relationship with profiles, which in turn has one-to-one relationships with student_profiles and faculty_profiles. A user has many user_skills (each referencing a row in skills) and many user_interests (each referencing research_interests). A user can have one github_connections record.
projects are owned by a user (owner_id) and have many project_skills, project_roles, project_members, and join_requests. Each project_member references a project_role. Each join_request references a project_role and optionally an ai_analyses record.
projects also have many tasks, milestones, documents, research_notes, and discussions; each discussion has many discussion_replies.

55. ROW LEVEL SECURITY STRATEGY
55.1 RLS Principles
Default deny: No access unless explicitly granted.
User-owned: Users can access their own data.
Project-scoped: Project data accessible to members only.
Role-based: Admin has elevated access.
Service role: Edge Functions use service role for authorized operations.
55.2 RLS Policies by Table
users
-- Users can read their own user recordCREATE POLICY "Users can view own user" ON users  FOR SELECT USING (auth.uid() = id);-- Users can update their own user recordCREATE POLICY "Users can update own user" ON users  FOR UPDATE USING (auth.uid() = id);-- Admins can view all usersCREATE POLICY "Admins can view all users" ON users  FOR SELECT USING (    EXISTS (SELECT 1 FROM users WHERE id = auth.uid() AND role = 'admin')  );
profiles
-- Public profiles visible to all authenticated usersCREATE POLICY "Public profiles visible" ON profiles  FOR SELECT USING (    visibility = 'public' OR user_id = auth.uid()  );-- Users can update own profileCREATE POLICY "Users can update own profile" ON profiles  FOR UPDATE USING (user_id = auth.uid());-- Users can insert own profileCREATE POLICY "Users can insert own profile" ON profiles  FOR INSERT WITH CHECK (user_id = auth.uid());
projects
-- Public projects visible to allCREATE POLICY "Public projects visible" ON projects  FOR SELECT USING (    visibility = 'public'    OR owner_id = auth.uid()    OR EXISTS (      SELECT 1 FROM project_members      WHERE project_id = projects.id AND user_id = auth.uid()    )  );-- Owners can update own projectsCREATE POLICY "Owners can update own projects" ON projects  FOR UPDATE USING (owner_id = auth.uid());-- Anyone can create projectsCREATE POLICY "Anyone can create projects" ON projects  FOR INSERT WITH CHECK (owner_id = auth.uid());
join_requests
-- Applicants can view own requestsCREATE POLICY "Applicants view own requests" ON join_requests  FOR SELECT USING (applicant_id = auth.uid());-- Project owners can view requests for their projectsCREATE POLICY "Owners view project requests" ON join_requests  FOR SELECT USING (    EXISTS (      SELECT 1 FROM projects      WHERE id = join_requests.project_id AND owner_id = auth.uid()    )  );-- Users can create own requestsCREATE POLICY "Users create own requests" ON join_requests  FOR INSERT WITH CHECK (applicant_id = auth.uid());-- Owners can update request statusCREATE POLICY "Owners update request status" ON join_requests  FOR UPDATE USING (    EXISTS (      SELECT 1 FROM projects      WHERE id = join_requests.project_id AND owner_id = auth.uid()    )  );
ai_analyses
-- Project owners can view analyses for their projectsCREATE POLICY "Owners view project analyses" ON ai_analyses  FOR SELECT USING (    EXISTS (      SELECT 1 FROM projects      WHERE id = ai_analyses.project_id AND owner_id = auth.uid()    )  );-- Users can view their own analysesCREATE POLICY "Users view own analyses" ON ai_analyses  FOR SELECT USING (user_id = auth.uid());-- Edge Functions can insert analyses (service role)CREATE POLICY "Service can insert analyses" ON ai_analyses  FOR INSERT WITH CHECK (true);

59.2 Fallback UI
When AI analysis is unavailable, the UI displays a clear notice: “We couldn’t generate an AI compatibility score at this time,” followed by guidance that the owner can still review the applicant’s profile manually — their skills, interests, and experience — and make a decision based on the available information. Two actions are offered: “Retry AI Analysis” and “View Profile.”
59.3 Retry Logic
Attempt 1 calls the AI provider; on failure, wait 1 second and try Attempt 2; on failure, wait 3 seconds and try Attempt 3; if that also fails, show the fallback UI.

79. AI RISKS AND LIMITATIONS
79.1 Explicit AI Limitations
AI can make mistakes. Compatibility scores are estimates, not facts.
GitHub activity does not prove expertise. It is supporting evidence only.
Self-declared skills may be inaccurate. AI cannot verify claims.
AI recommendations must be explainable. Black-box scores are not acceptable.
Final decisions remain with authorized humans. AI recommends, humans decide.
AI must not discriminate. No use of gender, race, religion, etc.
AI should not make high-impact academic decisions autonomously. Always human-in-the-loop.
AI scores are not scientifically objective. Clearly labeled as AI-estimated.
AI context is limited. Only authorized, minimal data is sent.
AI provider may change. Abstraction layer allows provider swap.
79.2 AI Disclaimer Text (UI)
“This compatibility score is AI-estimated based on available profile information. It is not an objective measurement of a person’s ability, skill, or potential. Final decisions should be made by humans based on a holistic review.”

82. FINAL PRODUCT ARCHITECTURE
The final architecture consists of four layers:
User (Browser) connects over HTTPS to the frontend.
Frontend (React + TypeScript + Tailwind) exposes Landing, Auth, Dashboard, Projects Discovery, Project Room, Profile, Explore, AI Recs, Admin, Settings, and Notifications pages, communicating via the Supabase JS Client.
Supabase Backend provides Supabase Auth (email/password, GitHub OAuth, email verification, password reset, session/JWT management); PostgreSQL with Row Level Security across Users/Profiles, Projects/Members, Tasks/Research, Documents/GitHub/Activity, and AI Analyses/Recs/Reports; Supabase Storage (avatars/, documents/); and Supabase Edge Functions (AI Service Layer, GitHub Integration, Notification Service, Admin Actions), which in turn call Gemini/OpenAI, the GitHub API, and Supabase Realtime.
External Services — Vercel (frontend hosting), GitHub (OAuth, repositories), and the AI Provider (Gemini/OpenAI).
